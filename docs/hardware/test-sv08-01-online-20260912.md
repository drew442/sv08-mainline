## Camera evidence and next check

USB Video Class descriptors advertise MJPEG and uncompressed YUY2. MJPEG frame
sizes are 1280×720, 800×480, 672×456, 640×480 and 320×240. Each advertises intervals
of 333333, 400000, 500000, 666666, 1000000 and 2000000 units of 100 ns, approximately
30, 25, 20, 15, 10 and 5 frames/s. Thus the preserved 640×480/15 fps camera target
has descriptor support; replacing this device is not justified by enumeration.

`v4l2-ctl` is absent from this bring-up host. No package was installed to perform
the inspection. After reading descriptors with `lsusb -v -d 364d:6366`, a bounded
Python query enumerated kernel capabilities, formats, frame sizes and intervals.
The ARM64 Linux `videodev2.h` ioctl constants, structure sizes and field offsets
were checked with a cross-compiled C probe under QEMU before the query. Source,
ABI results and raw output remain private and are hash-bound in the observation.
This one-off query fills the missing-tool gap; use the baseline's packaged
`v4l2-ctl` for subsequent general diagnostics.

The unprivileged device open was denied. Existing noninteractive sudo access
allowed `O_RDONLY|O_NONBLOCK` opens and only `VIDIOC_QUERYCAP`, `VIDIOC_ENUM_FMT`,
`VIDIOC_ENUM_FRAMESIZES` and `VIDIOC_ENUM_FRAMEINTERVALS`. Descriptors were closed
afterward. No format-setting or stream-start ioctl was issued. The capture node
reports `MJPG` and `YUYV`; MJPG 640×480 has intervals 1/30, 1/25, 1/20, 1/15, 1/10
and 1/5 seconds. YUYV 640×480 reports only 1/30. The second node does not advertise
the ordinary video-capture capability used by this query.

Negotiation, sustained capture, delivered frame rate and ustreamer integration
remain untested. Kernel enumeration confirms the intended MJPEG mode is offered;
it does not validate the complete camera workflow on the new image.
