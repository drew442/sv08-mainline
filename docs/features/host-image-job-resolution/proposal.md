# host-image-job-resolution: finish review of an interrupted image operation safely

Kind: feature. Author: source-review-job-suggester. Date: 2026-09-12.
Dependency: independent recovery image delivery. Requirement: [decision 0010](../../../docs/decisions/0010-host-administration-and-recovery-ui.md). This bounded proposal completes an existing browser administration requirement; it grants no hardware authority.

## Problem and evidence

`runtime/sv08_admin_jobs.py` blocks all new image operations after one uncertain worker outcome; `docs/hardware/host-admin-image-jobs.md` explicitly has no browser resolution. An administrator can observe interruption but cannot finish its review and proceed to a separately reviewed safe-source cancellation. The required follow-on is already listed in `docs/hardware/host-os-tasks.md:122` and follows decision 0010's browser administration/data-preservation requirements.

Current tests provide a concrete baseline: `tests/test_admin_jobs.py::test_real_worker_killed_inside_transaction_is_not_replayed` kills a worker inside a substituted sleeping backend, observes interruption and rejects a new identity. Publication-failure and lost-acknowledgement tests also preserve uncertainty. These tests were inspected, not rerun in this suggestion; their backend is not an independently running RAUC install service. `LIMIT = 128` separately causes history-full refusal with no identity eviction (`test_capacity_never_evicts_retry_identity`).

The private `local/feature-workflow/job-resolution-intake.md` supplies source-level invariants and version-specific primary evidence. Baseline package inventory selects Debian RAUC `1.13-3+deb13u1`; upstream 1.15.2 remains an offline integration candidate in decision 0007. Inspected, archive-hash-verified upstream 1.13/1.15.2 service sources can reset public Operation to idle on rejection while internal busy remains true. Successful fresh GetSlotStatus checks the internal busy guard in those sources, but is only point-in-time evidence. Exact Debian source/patch behavior and the eventual composed service selection remain unresolved. `Admission` presently barriers printer services, not every RAUC client. A service-owner change, disappeared service, exited CLI or released worker lock cannot certify inactivity.

## Intended outcome

An administrator opens an interrupted receipt, sees its original identity/outcome and a bounded evidence review, and explicitly finishes the receipt review **without rewriting an unknown result as success or refusal**. Once supported RAUC writers are excluded and the backend/journal permit it, the administrator separately reviews the existing cancellation operation from the preserved source. Reconnect retrieves the same disposition; no install is repeated, target is never implicitly selected and no trial is called healthy.

Recommend **ambiguous receipt resolution before archive rollover**. One crash can block the accepted update/cancellation journey immediately, and the missing service-side exclusion is relevant to any safe subsequent mutation. Rollover becomes necessary after 128 retained identities and cannot resolve an uncertain live receipt by itself. This priority follows data safety and completing an existing failed-operation journey rather than minimizing implementation effort. It does not imply rollover is optional for first-release completion.

## Scope and alternatives

### Proposed smallest useful scope

- A read-only evidence review and an explicit durable administrative disposition for **one unresolved receipt**, preserving original ID, complete plan and outcome, with a hash-bound bounded evidence snapshot. No implicit reconcile or slot mutation occurs when opening, refreshing or acknowledging.
- A truthful selected-service identity/inactivity check, including system bus owner continuity, actual service executable/version and backend configuration/slot identity. Refuse unsupported version, unavailable owner, failed/busy query, transitioning worker or stale state. Pin or verify the exact baseline executable used in acceptance; the known upstream candidate can be covered additionally, not substituted silently for baseline evidence.
- A common exclusion mechanism for **supported project RAUC mutation paths**, including install and boot-mark/cancel callers. The implementation must show how those paths, assembled D-Bus access policy and maintenance entry points participate. Keep this specific to image/backend mutation; no generic task framework or new network daemon. Do not promise prevention of uncooperative privileged/root access. Direct privileged intervention is outside the supported protocol and requires fresh inspection; observed owner/configuration/activity changes invalidate review.
- Hold execution and supported-writer exclusion while rechecking evidence and committing the administrative disposition. A dead worker must not leave a surviving RAUC service install mistaken for idle. A late queued unit must not claim a resolved receipt. Define lock order so ledger/status polling stays responsive; do not hold the ledger lock across installation or device hashing.
- After disposition, preserve transaction gates. A live installing/staged/arming transaction still blocks fresh staging. A separately confirmed cancellation may use the existing `HostImages`/`Transaction.cancel` path only from its safe preserved source, with existing idle admission, bootloader rechecks and non-deployable refusal. Unknown outcome remains visible after that cancellation. No automatic retry, arm, reboot or health promotion.
- Stage the actual helper/service/UI/policy changes together and include a migration that reads old receipts without reinterpreting interruption. Choose an explicit disposition record/schema rather than adding `interrupted` globally to `TERMINAL`.

Likely source ownership: `runtime/sv08_admin_jobs.py`, `sv08_admin.py`, `sv08_admin_images.py`, `sv08_rauc.py`, narrowly necessary admission/configuration integration, `ui/host/app.js`, runtime/UI staging, and selected service/browser/disposable backend tests. Preserve current snapshot pins and host/MCU policy. Any necessary custom code fills the observed missing receipt/exclusion integration; keep it outside upstream RAUC and retire it if a supported upstream/project transaction service supplies equivalent semantics. This suggestion does not authorize edits yet.

### Comparison with rollover-first

| Choice | Useful completed outcome | Boundary/cost |
| --- | --- | --- |
| **Resolution first (recommended)** | One worker/CLI failure no longer permanently strands safe-source cancellation; uncertainty remains honest. | Requires real service inactivity evidence, supported-writer exclusion, and a service-backed orphan-install test. These cannot be waived as “just receipts.” |
| Archive rollover first | Full all-terminal history can admit more distinct jobs while old retries return their original result. | Smaller persistence/UI slice, but an interrupted row remains blocking; does not solve service-side orphan writes or safe cancellation after failure. |

Archive rollover should follow as a separate bounded feature. A reasonable proposal can retain at most **eight archived batches of up to 128 complete receipts plus the active 128**, with explicit encoded-byte/evidence limits and temporary-space reserve measured before adoption. That is a finite maximum of 1,152 retained identities, **not unlimited lifetime retention**. The exact archive byte budget must be derived from the final resolution schema and available `/data` budget, not invented as a proven fit here. All old identities/outcomes remain authoritative; lookup spans archive and active rows before new admission. At total capacity, fail closed with a clear maintenance reason. No TTL/LRU deletion, export-then-delete, unknown-old-ID-as-new behavior or epoch migration is included in that follow-on. Increasing the finite ceiling again requires an explicit measured review.

For the resolution proposal, **128-full history stays blocked to new image jobs**; administrative evidence review itself must remain readable/usable. A fresh cancellation receipt also needs capacity, so that corner completes only when the rollover follow-on lands. Do not hide it, evict a row or quietly reserve extra executable identities in this feature. Receipt resolution must work below that limit first; archive rollover then composes with it. This explicit limitation keeps the two deliveries bounded without changing the accepted final workflow.

No new updater, automatic scheduler, signing/health mechanism, generic broker framework, kernel choice, disk layout or independent recovery redesign. A raw “reset interrupted receipt” button and rollover that drops deduplication information are rejected alternatives.

## Acceptance and task split

Suggested one implementation task ID: `implement`. Coordinator assigns these stable check IDs in the selected record; a separate verifier reviews final composed evidence. No task record is created by this note.

1. **review-is-observation** — Disposable controller/browser fixture captures receipt, state/journal, boot, worker lifecycle and selected RAUC identity. Opening/refreshing/cancelling review writes no transaction/slot state and never calls `Transaction.reconcile`. Busy/missing/corrupt/owner-changed evidence gives a useful refusal.
2. **orphan-service** — In a disposable service-backed RAUC environment using the exact selected package, start a real signed paired install with a deterministic service-side barrier; kill/disconnect its CLI or image worker while leaving the service alive. Prove it remains busy; receipt resolution and cancellation refuse and no second install starts. Release the barrier and obtain fresh same-owner internal-busy-guarded evidence before a new review can proceed. A sleeping mocked backend or merely inactive systemd worker does not satisfy this check. Test policy permits disposable instrumentation only; no fixture handler enters production configuration.
3. **idle-proof** — For every claimed supported version, reproduce or reject the public Operation-idle/busy discrepancy and verify the chosen stronger probe. Timeouts, service restart/name-owner replacement and unexpected executable/configuration invalidate the plan. No probing InstallBundle call on real targets.
4. **writer-exclusion** — Concurrent supported install/mark/cancel entry points cannot begin between admitted final evidence check and disposition/backend action. Test the assembled access policy and all supported routes, not only two callers honoring a test flock. State the uncooperative-root boundary explicitly; do not label it prevented.
5. **disposition-durability** — Original identity, plan and unknown outcome remain byte- or canonically bound to the disposition. Same/different-content retries, lost acknowledgement, late worker arrival, reboot, and failure around every durable publication preserve at-most-once admission. Changed evidence refuses; no stale review authorizes a mutation.
6. **safe-source-journey** — Actual browser interruption → inspect → review disposition → reconnect → separately review cancellation below capacity, using disposable backend/transaction integration. Original source stays selected, pending state clears only after verified disarm, and user-data/source images remain preserved. Target boot, changed original boot, failed disarm, unavailable adapter and trial-health cases retain their required refusal. Existing customized-source cancellation remains usable where already allowed.
7. **regression-and-bounds** — Relevant admin/jobs/transaction/admission/backend tests plus composed UI/staging checks pass. Measure added bytes, bounded evidence storage and temporary publication reserve; no-space/corruption refuse without deleting receipts. History stays responsive during long operations. The 128-full limit and future rollover dependency remain explicit. No ordinary test reruns beyond those affected without new evidence.

If selected-version evidence or supported-writer exclusion cannot be completed, retain the current gate and report the exact blocker. Do not ship only a success-looking “acknowledge” path or silently reduce acceptance. The coordinator may select the separately reviewed rollover slice as an offline alternative if necessary; this note grants no approval for either.

Hardware activation remains under the existing `docs/hardware/host-os-tasks.md#human-and-powered-printer-tasks` and `docs/hardware/test-sv08-01-recovery-tasks.md` requirements, with named-profile/recovery evidence before any writes. The independent recovery image remains ahead of this proposed delivery; physical HDMI/touch/boot/rollback tests are not claimed by these service/browser fixtures.
