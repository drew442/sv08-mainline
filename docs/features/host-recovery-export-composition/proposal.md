# host-recovery-export-composition: save user data from the independent recovery OS

Kind: feature. Author: recovery-composition-suggester (`root/job_resolution_approver`, new suggestion role). Date: 2026-09-12. Not approved.
Requirement: `docs/decisions/0010-host-administration-and-recovery-ui.md`. Dependencies: verified delivery of `host-recovery-independent-image:implement` and existing approved `host-image-job-resolution:implement` delivery order. This private draft creates no task record or queue entry.

## Problem and evidence

The existing exporter and media provider can save preserved files through actual GTK in workstation fixtures, but production export is unavailable in the independently booted compressed recovery OS. The provider neither supports its `/usr` backing chain nor has a trusted mount preparer to produce the immutable-policy-bound per-boot context. An owner can inspect diagnostics but cannot complete Save user data there.

The private `local/feature-workflow/recovery-composition-draft/intake.md` records inspected source paths, mutable worktree status, actual provider invariants and local QEMU primary interfaces. Existing completed evidence is in `docs/hardware/host-recovery-media.md` and `host-recovery-readback.md`. The current independent image implementation is still mutable; its draft ADR0014/initramfs/VM harness are candidate inputs, not completed compatibility. No service, VM or mount test ran for this suggestion.

## Intended outcome

Boot the verified independent ARM64 candidate with reviewed virtual system/source media and an initially connected removable FAT destination. A trusted startup preparer identifies all protected media, prevents source writes before its first mount, mounts the reviewed source without journal replay and the destination using bounded policy, then publishes a boot-bound context under shared admission. The normal installed GTK entry offers Save user data, displays target-specific review, supports cancel/apply, and reports a verified archive or a useful failure. A damaged state registry remains exportable without initialization. Missing or unsafe media leave useful diagnostics and disabled export.

This is a complete local export composition, following the already approved recovery and job-resolution work. It closes the gap between existing offline components and a working independent recovery user journey. It does not claim physical media/input, power-loss or board support, or complete signed restoration.

## Scope and alternatives

One implementation owner adds a small trusted preparer and startup integration, exact compressed-usr admission to the existing provider, coherent policy/manifest/context generation and a full ARM64 production-entry test. Reuse upstream mount/blkid/block-RO interfaces and selected kernel drivers, existing MediaLease/GTK/controller/exporter, package builder and VM harness. No upstream checkout modifications, new service framework, network daemon or new package/kernel selection without ordinary pinned intake evidence. Document custom-code provenance and retirement when upstream recovery integration provides equivalent identity/preparation/admission semantics.

The preparer is a separate explicit operation from read-only inspection/export. It runs only for a reviewed recovery profile, validates immutable trust files and complete supported system-media inventory before mounting, and obeys the fixed `/run/sv08-recovery/media.lock`. No UI-selected raw path, guessed serial/UUID, formatting, automatic filesystem repair or borrowed A/B libraries. Source partition and whole medium must be block RO before the first source filesystem mount; ext4 uses ro,noload/norecovery. Review and refresh perform no preparation. FAT mounting is target-specific and may write destination metadata; preserve existing files and never call it read-only preparation. Missing/failed/stale context leaves diagnostics usable.

Add exactly one admitted `/usr` chain: reviewed physical ext4 root -> root-owned regular immutable compressed file -> read-only zero-offset bounded-mapping loop -> exact SquashFS `/usr`. Independently validate both the early boot binding and provider policy/manifest binding, filesystem/device/inode identity, hash/size, mount options, no writable aliases or unexpected holders/submounts. Do not generalize production loop acceptance. Reject extra virtual source/destination media, overlays and unknown stacks. Keep complete namespaces, mount snapshot and same-medium alias checks; no fixture flag or test-generated expected snapshot grants production trust.

For the VM, prefer SCSI disks with explicit WWN/serial and a removable USB SCSI destination; installed QEMU's documented device properties support that configuration. Guest sysfs must prove each attribute, removable bit and diskseq before the profile is recorded. An exact SCSI early-root profile and necessary selected-kernel modules may replace the current vda-specific profile; root stays a 512 MiB ext4 envelope. A narrowly evidenced virtio serial integration is an alternative, not permission to synthesize sysfs. Use regular-file QEMU backends only. Source/system GPT media include unmounted A/B partitions and a further protected medium to test inventory completeness. Open recovery/source read-only from VM launch for the preservation control and separately prove guest block-RO ordering with disposable writable input before mounting.

Startup supports bounded initially attached reviewed FAT media; arbitrary hotplug discovery, ejection, LAN input, restore, boot-slot selection and host image administration are excluded. On replacement/removal, stale review refuses; restarting/repreparing the bounded session is acceptable with a displayed reason. Completing hotplug/ejection remains later work. Existing policy/contexts require explicit version/migration treatment: accept valid old uncompressed preparation where previously supported, never reinterpret a fixture or fabricate missing trust.

Retain factory 7,818,182,656-byte layout and 512 MiB recovery partition. Measure additional packages/modules/code, compressed/envelope occupancy, temporary workspace and peak memory; preserve complete GTK/accessibility/input closure and the exporter single-pass readback. No physical write/boot/format authorization follows from approval of this offline delivery.

Alternatives: keep export disabled (safe but leaves accepted journey incomplete); reuse workstation loop fixtures (does not establish production composition); whitelist SquashFS or trust a marker alone (insufficient backing proof); build a generic automounter/restore broker (unnecessary scope). The proposed precise backing-chain and preparer composition is the smallest useful delivery.

## Acceptance and task split

Suggested task `implement`, offline, after both dependencies above; separate approver and delivery verifier are required. Stable check IDs:

1. **profile-and-trust** — Reinspect final independent-image artifacts. Record exact VM/controller/kernel-module/package inputs and actual guest stable IDs, diskseq, geometry and UUIDs. Generate coherent root-resident manifest/policy without circular hashing. Omitted unmounted system medium, aliases, duplicate identities, wrong root/token/hash and unknown devices refuse before preparation; destination cannot impersonate protected media. No test-loop or fixture kind is accepted by normal entry.
2. **preserve-before-mount** — Instrument disposable boot/preparation to prove no source filesystem mount or journal replay precedes whole-medium AND partition block-RO verification. Test dirty-journal source without repair and compare complete source/recovery images before/after success and failures. Reject already mounted/writable aliases, unknown topology and unexpected active participants. Actual guest preparation uses fixed MediaLease and publishes context only after successful validated preparation; failed partial preparation cannot enable export.
3. **compressed-chain** — Normal provider accepts only the reviewed real `/usr` mount/backing chain. Mutate manifest/content, backing file/loop, offset/sizelimit, RO flags, aliases, mount identity and unexpected usr submounts in disposable tests; each prevents admission or publication. Validate switch_root pathname behavior against real loop metadata. Preserve legacy uncompressed contract and generic virtual-storage refusal; no widening of namespace exemptions.
4. **independent-gtk-export** — Full ARM64 boot runs its own ordinary installed service/main(), with no injected adapter, borrowed library or fixture switch. Real removable FAT destination enables chooser, review cancel, apply and verified archive. Exercise actual keyboard, mouse and supported independent virtual touch; export damaged registry and representative config/SQLite-WAL/Unicode files without repair. Verify full archive/member hashes and preservation of existing destination files. Repeat from fresh boot, retaining diagnostics on absent/corrupt/untrusted preparation.
5. **lease-and-change** — Real concurrent preparer/export/media-change participant refuses under fixed lease, including readback/publication/fsync. Real guest USB removal/replacement and reused filesystem UUID/device number invalidate plans through diskseq/stable topology; no stale context or review publishes success. Verify operation-owned cleanup and explicit cleanup failure diagnostics without deleting older files. Full mount and namespace checks stay responsive and valid during GTK lifecycle.
6. **composition-and-bounds** — Stage/build exact matching runtime, service and trust files; report compressed/uncompressed and allocated bytes, remaining blocks/inodes, preparation workspace and peak VM memory. Keep 512 MiB and factory layout checks, selected pins and full input/accessibility closure. Run affected exporter/provider/GTK/builder regressions, default inspection/refusal checks and proportionate JSON/Markdown/diff/gitlink checks. Record reproducible artifact hashes and before/after capability evidence. No-space and archive corruption refuse. Clearly distinguish full-VM composition from physical durability or release acceptance.

If actual production namespaces, stable media identity or compressed-chain proof cannot meet these checks, retain export refusal and report a concrete blocker. Do not deliver only a preparer that fabricates expected observations or call a mocked-provider success complete.
