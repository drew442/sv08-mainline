# network-emmc-authenticated-claim: Authenticate the one-shot write claim

Kind: feature. Author: root/coordinator. Date: 2026-09-27.

## Problem and evidence

The H616 writer's `claim_once()` in
[`emmc_image_writer.c`](../../../tests/fixtures/sd-network-root/emmc_image_writer.c)
uses plain HTTP and accepts a successful response when its body matches a
literal job ID and descriptor hash. The Python `ClaimHTTPServer` in
[`sv08_emmc_job.py`](../../../tests/sv08_emmc_job.py) sends no authenticated
receipt. Existing tests prove a durable single-use state against duplicate
requests and a lost acknowledgement, but do not prove the guest can distinguish
the real service from a forged HTTP peer. A network peer that can spoof the
claim endpoint can therefore make the guest proceed without the real claim
state having been consumed.

The [H616 commissioning report](../../hardware/host-network-emmc-h616-adapter-offline-20260926.md)
lists the claim and boot trust path as unresolved. The exact v5 artifact map is
now pinned by the [offline map delivery](../../hardware/host-network-emmc-v5-image-map-20260927.md),
but that work did not enable physical construction or use.

## Intended outcome

Before: the writer trusts a plain HTTP status and body as proof that the
one-shot job was durably consumed.

After: the service returns a signature over a versioned receipt containing the
job ID, immutable descriptor hash, and a fresh random challenge generated by
the guest. The service signs only after durably consuming the claim. The guest
verifies the signature against a locally pinned public key, then checks every
bound field before it can open the target. Missing, forged, altered, wrong-job,
stale, or replayed receipts fail closed. A lost acknowledgement consumes the
job and does not cause an automatic retry or rearm.

Use an established Ed25519 implementation with recorded source/version and a
bounded static guest integration. Do not add hand-written cryptography. If a
reviewed static implementation cannot fit the existing image and 8 GB layout,
stop with measurements and an alternative for review; do not weaken receipt
authentication. Private signing material stays on the host service and out of
the guest, repository, and public evidence. Only the verifier key may be
embedded in the nondeployable commissioning candidate.

## Scope and alternatives

Implement the request/receipt protocol, durable server signing, guest
verification, candidate key pinning, synthetic QEMU regressions, and public
offline evidence. Use a cryptographically random per-invocation challenge from
the guest OS and fail closed if it cannot be obtained. Sign a canonical,
versioned byte representation so the guest can verify exactly the fields it
expects. Keep one-shot consumption durable before signing; any ambiguous state
remains consumed. Verify challenge freshness by exact equality with the
unpredictable value from the current invocation.

Keep the default SD/NFS diagnostic, A/B updater, boot policy, and existing H12
human-task entry unchanged. Do not build a bootable writer SD image, provision
production secrets, access printer hardware, or perform a physical write. The
H616 candidate remains nonbootable and nondeployable, and all hardware and
release checks remain separate. The existing host-supplied claim port should
remain bounded by candidate policy rather than being trusted as authority.

The alternative is to leave the writer inert and defer H12. TLS with a pinned
server identity is also possible but brings TLS setup and certificate lifetime
into the static guest. A signed, challenge-bound receipt addresses the specific
forged-acknowledgement gap while reusing the existing signed-job trust model.
The custom writer remains temporary commissioning code; retire it if a
maintained upstream mechanism provides the same target, image, one-shot and
readback contract.

## Acceptance and task split

- **claim-01** — A successful receipt signature binds the current job ID,
  descriptor SHA-256, and fresh challenge; the guest accepts a valid receipt
  and rejects an unavailable or invalid system random source.
- **claim-02** — Forged, modified, wrong-key, wrong-job, stale-challenge,
  replayed, truncated, and malformed receipts refuse before the target is
  opened or modified.
- **claim-03** — The server durably consumes the one-shot state before signing;
  duplicate/replayed claims remain refused, and a lost response cannot retry or
  rearm the job. Test interruption around durable state publication.
- **claim-04** — Full, fault, and abrupt QEMU paths and the default diagnostic
  regressions pass. Record crypto source/version and binary-size delta; prove
  the candidate stays within the reviewed 8 GB image layout, nonbootable and
  nondeployable. Bind evidence to source and manifest hashes.

All checks are offline against disposable synthetic QEMU media and test keys.
No human interaction is required for this change. Reuse H12 only after the
remaining boot trust path, live CID/dev_t mapping, exact candidate and target,
recovery operation, independent high-consequence review and explicit physical
write authorization are ready.
